# 生成 PPT（pptx）

把方案汇报内容填进用户提供的 .pptx 模板，生成**排版精美、可演示**的成品，落在会话工作区里。

**禁止**跳过需求确认直接生成简陋 bullet 页；**必须**走完下方流程后再调用脚本。

---

## 总流程

```
需求确认 → **取得模板** → 大纲确认 → 准备 tmp/ppt-work → 配图准备 → 组装 JSON → 生成 → 落到工作区
```

**核心原则**：
- **唯一路径：模板改字/换图/裁剪**。本部署没有模板库，模板只能来自用户——工作区里的 .pptx 文件。
- **取得模板**：先在工作区里找 `.pptx`。找到多个就问用户用哪个；一个都没有就**停下来向用户要一份**，并说明这里没有用户模板可选。模板的版式信息用 `inspect-template.mjs` 现场解析，不存在任何元数据库。
- 生成流水线：`unpack-pptx.mjs` 解压用户模板 → 写 `ppt-fill-spec.json` → `apply-unpacked-patches.mjs` → **`compose-slides-from-spec.mjs`（输出页数 < 模板页数时必做）** → `pack-pptx.mjs`。
- 占位符索引**不入库**；写 spec 时用 `inspect-template.mjs` 现场解析 `shapeIndex`。
- 没有模板库，因此没有「保存模板」这一步。用户想复用某个模板，让它留在工作区即可。
- 需替换的内容：文字（`textPatches` / title/bullets）、**与场景不符的示例图**（`images[].path`）；纯装饰/背景保留在模板 XML 中。

---

## 第一步：需求确认（必做）

用户提出做 PPT 后，**先逐项确认**，信息不足时追问，不要假设。可用对话分批收集，一次问太多用户会跳着答。

### 1.1 内容与结构

| 维度 | 要问什么 | 默认推断 |
|------|----------|----------|
| 主题与目的 | 汇报什么？给谁看？（业主汇报 / 内部评审 / 竞赛答辩 / 课程展示） | 从对话上下文推断 |
| 页数 | 期望多少页？有无硬性限制？ | 8–15 页 |
| 内容来源 | 基于本次对话、业务工具查询结果、用户上传文档，还是混合？ | 本次对话已确认要点 |
| 章节结构 | 需要封面、目录、章节分隔、结语/Q&A 吗？ | 封面 + 正文 + 结语 |
| 详略 | 每页要点为主还是大段叙述？是否需要演讲者备注？ | 要点为主，备注可选 |

### 1.2 视觉与品牌

| 维度 | 要问什么 | 默认 |
|------|----------|------|
| 风格气质 | 商务稳重 / 建筑专业 / 科技感 / 简约留白 / 活泼创意？ | 建筑专业、商务稳重 |
| 主色 / 辅色 | 有无品牌色或项目 VI？（给 hex 或描述） | 深蓝 `#1F4E79` + 浅灰底 |
| 字体偏好 | 标题/正文字体？（如微软雅黑、思源黑体、Arial） | 微软雅黑 |
| 模板 | **工作区里有没有 .pptx？** 见 §2.1。没有就向用户要——这里没有用户模板 | 必须由用户提供 |

### 1.3 配图

| 维度 | 要问什么 | 默认 |
|------|----------|------|
| 配图策略 | 每页都要图？仅封面/章节页？还是纯文字？ | 封面 + 关键页配图 |
| 模板示例图 | 模板里自带的示例照片/插图是否保留？ | 先逐页审，场景相符保留，不符再换 |
| 图片来源 | 用户上传或工作区里已有的图，**你自己看过再复用**；没有合适的就**保留模板原图** | 先用用户给的图，其次保留模板原图 |
| 图风 | 写实效果图 / 示意图 / 图标插画 / 与项目风格一致？ | 建筑效果图风 |
| 图表 | 是否需要数据图、流程图、对比表？ | 按内容需要 |

### 1.4 输出

| 维度 | 要问什么 |
|------|----------|
| 文件名 | 如 `XX项目方案汇报.pptx` |
| 语言 | 中文 / 中英双语 |

**确认方式**：把汇总后的需求清单发给用户过目（主题、页数、风格、配色、模板、配图方案），用户点头后再进入大纲阶段。

## 第二步：取得模板

本部署**没有模板库**。模板只有一个来源：会话工作区里的 `.pptx` 文件。

### 2.1 找模板

```bash
ls *.pptx **/*.pptx 2>/dev/null
```

- 找到一个 → 用它，并把文件名念给用户确认。
- 找到多个 → 列出来问用户用哪个，不要替他选。
- **一个都没有** → 停下来向用户要一份 `.pptx`，并说明这里没有用户模板可选。
  给一份排版简陋的自制文件，比诚实地要一次模板更浪费他的时间。

### 2.2 解析版式

模板的页数、版式、占位符、示例图，全部**现场解析**——不存在任何元数据库，也没有
需要注册或保存的步骤。用户想复用某个模板，让它留在工作区即可。

```bash
node <技能基准目录>/scripts/inspect-template.mjs <模板>.pptx
node <技能基准目录>/scripts/inspect-template.mjs <模板>.pptx --slide=2
```

解析不出来时，向用户确认模板页型，手动指定 `sourceSlideIndex`。

### 2.3 关键概念：`sourceSlideIndex` ≠ 最终页序

- 模板可能有 **25 页**，用户大纲只要 **10 页**。
- `sourceSlideIndex` 表示「**从模板第几页取版式并填内容**」，不是最终 PPT 的第几页。
- `apply-unpacked-patches` **只在原位改字/换图**，**不会删页、不会重排**。
- 若只 patch 不 compose，成品仍是模板全页数——**必须**跑 `compose-slides-from-spec`。

### 2.4 标准步骤

**禁止**用 PowerShell `Get-Content | node` 传 JSON（中文会变成 `????`）。spec 一律作为
**文件路径**传给脚本。

```bash
mkdir -p tmp/ppt-work out
node <技能基准目录>/scripts/unpack-pptx.mjs <模板>.pptx tmp/ppt-work
```

1. 解压模板到 `tmp/ppt-work`
2. 审模板自带示例图（§4.0）——你自己看图，判断场景是否相符
3. 大纲确认：**输出页 ↔ 模板页 `sourceSlideIndex`** 对照表
4. 写 `tmp/ppt-fill-spec.json`（见 §5.1）
5. `apply-unpacked-patches.mjs` → `compose-slides-from-spec.mjs`（页数裁剪时**必做**）
   → `pack-pptx.mjs` 输出到 `out/`

## 第三步：大纲确认

基于已确认需求与对话内容，给出**分页大纲**（表格或列表）：

```
P1  封面     标题、副标题、日期
P2  目录     章节列表
P3  章节页   「项目背景」
P4  内容页   背景要点 + 配图（AI 生成区位示意图）
...
Pn  结语     谢谢 / Q&A
```

用户确认或修改大纲后，再进入配图与生成。**不要**未经确认就生成。

大纲须包含 **输出页 ↔ 模板页（sourceSlideIndex）** 映射；确认后 `slides[]` 顺序必须与输出页一致。

用户确认大纲后、进入配图与生成前，准备工作目录。工作区已经是每用户隔离的，中间态
统一放 `tmp/`：

```
tmp/ppt-work/          解压后的模板
tmp/ppt-fill-spec.json 填充规格
```

| 步骤 | 命令 |
|------|------|
| 建工作目录 | `mkdir -p tmp/ppt-work out` |
| 解压模板 | `node <技能基准目录>/scripts/unpack-pptx.mjs <模板>.pptx tmp/ppt-work` |

- **同会话改稿**：复用现有 `tmp/ppt-work` 与 `tmp/ppt-fill-spec.json`；**不要**再 `--new-ppt`，那会清空它们

记下 **`tmp/ppt-work`**。模板副本、`ppt-work/`、`ppt-fill-spec.json`、配图都写入 `tmp/ppt-work`。

**禁止**删除整个 `tmp/` 或其他 session 的目录。

## 第四步：配图准备

### 4.0 模板自带示例图（有模板时必审）

商业模板常在封面/内容页嵌入**示例照片、产品图、人物图**。生成前须判断是否与用户本次汇报**场景、行业、地域、题材**一致。

#### 怎么查

| 模板来源 | 示例图 metadata 从哪读 |
|----------|------------------------|
| **工作区模板** | 解压后直接看 `tmp/ppt-work/ppt/media/` 里的图，你自己判断场景是否相符 |
| **内置** | `read assets/{Name}.json` → `ImagesJson.images[]` |

对拟用的每个 `sourceSlideIndex`，找 `slideIndex` 相同的条目，按 `picIndex` 阅读 `summary`。

#### 怎么判（内容是否该换）

| 类型 | 示例 | 建议 |
|------|------|------|
| 纯装饰 | 几何块、线条、渐变、纹理、无具体含义的 abstract 图 | **保留**，不必生图 |
| 通用商务 | 握手、会议、办公场景，与用户行业无冲突 | 可保留；用户要求写实时再换 |
| 场景相关 | 建筑效果图、湖泊现场、产品实拍、特定城市风光 | 必须与本次主题一致，**不符必换** |
| 带文字/品牌 | 模板厂商水印、他人项目名、英文 placeholder 配图 | **必换**（见下方「文字艺术槽」） |

#### 槽位角色（换图前必判，与内容类型正交）

同一页可有多个 `picIndex`，**每个槽位单独判断**。替换图须在**视觉角色**上与原槽位一致，不能只因「主题不符」就塞一张无关风格的图。

| 槽位角色 | `summary` 线索 | 替换策略 |
|----------|----------------|----------|
| **主图/背景照片** | 人物、建筑、风景、实拍、全景 | 可换本次主题相关的**全彩照片**；构图横/竖与原槽位相近 |
| **纯装饰纹理** | 抽象、几何、水墨底纹、无明确主体 | **优先保留**；要换也只换同类抽象装饰 |
| **文字艺术图** | 书法、手写体、标语、海报字、summary 含「含文字品牌」 | **禁止**换成无字风景/产品图；须生**同风格带字图**，文案用本次标题/口号/章节名 |
| **效果/单色层** | 黑白水墨、高对比、剪影、笔触蒙版 | **默认保留**；若必须换，只换同类单色/高对比图，**禁止**换全彩实景 |

#### 模板 XML 效果约束（技术层，必查）

`apply-unpacked-patches` **只替换 media 文件，不会修改 slide XML 中的颜色/二值化效果**。写 spec 前，对**拟替换**的每个 `picIndex`，读 `tmp/ppt-work/ppt/slides/slide{N}.xml`，找到对应 `<a:blip r:embed="...">` 子节点是否含：

| XML 效果 | 含义 | 约束 |
|----------|------|------|
| `<a:biLevel/>` | 强制二值化（高对比黑白） | **禁止**写入全彩图；保留原图，或换单色/文字艺术图 |
| `<a:grayscl/>` | 强制灰度 | 禁止写入全彩图；保留或换灰度风格图 |
| `<a:duotone/>`、`<a:lumMod/>` 等 | 色调/亮度滤镜 | 换图须匹配效果，或**保留**原 media |

**典型误例**：封面 `picIndex 0` 为右侧主图（可换全彩河道图），`picIndex 1` 带 `<a:biLevel/>` 为左侧文字/笔触层——对其写 `images: [{ index: 1, path: "彩色水纹.jpg" }]` 会在 PPT 里被渲染成黑白，**不符合预期**。

#### 怎么处理

- **保留**：该 `picIndex` **不要**出现在 spec 的 `images[]` 里。
- **同型替换**：AI 生图 / 用户素材 → `images: [{ "index": N, "path": "tmp/slide-01-cover.jpg" }]`（`index` = `picIndex`）；prompt 须符合上表**槽位角色** + **XML 效果**。
- 同一页多张图：**按 picIndex 分别**决定保留/替换，不要「整页统一换图」。
- 大纲或需求确认可简述：「封面 `picIndex 0` 换河道实景；`picIndex 1` 为 biLevel 文字艺术层，保留模板原图」。

**禁止**不审槽位就全页生图；**禁止**场景不符仍保留主图；**禁止**把全彩实景塞进 biLevel/grayscl 槽位；**禁止**文字艺术槽换成无字随机图。

  ### 4.1 用户提供的图片（优先复用，再决定是否生图）

用户通过**对话附件**或直接放进工作区的图片，在调用生图工具之前，**必须先逐张分析**，能直接用的就复用，**不要重复生成**。

#### 流程

1. **收集**：列出本轮可用的用户图片（工作区里的路径；复制到 `tmp/ppt-work` 下再引用）。
2. **分析**：对每张图调用 Java **自己看图**（工具列表中有则必用）。prompt 示例：
   ```
   请用中文简要描述图片的场景、主体、风格与配图类型（装饰/通用/特定场景/含文字品牌），100字以内。
   ```
3. **匹配**：对照大纲各页、§4.0 中**判定需替换**的 `picIndex` 槽位（含槽位角色与 XML 效果约束）：
   - 场景、行业、构图、色调与目标页/槽位一致 → **直接复用**（复制到 `tmp/`，写入 spec `images[].path`）
   - 纯装饰且模板该槽位本就可保留 → 可不换，不必强行塞用户图
   - 无合适匹配 → 该槽位进入 §4.2 生图
4. **记录**：向用户简述「封面用您上传的河道图；第 4 页无合适素材，将 AI 生成示意图」。

#### 原则

- **一张用户图可复用于多个槽位**（若内容相符）；**不要**对有可用用户图的位置再调生图。
- 用户图须满足 §4.0 **槽位角色**（如文字艺术槽不能塞无字风景图）。
- 看图就直接看——本部署的模型收图片，工作区里的图片文件你自己打开判断，没有单独的审图接口。

### 4.2 AI 生图（用户素材不足时）

对大纲中标注了配图、§4.0 **判定需替换**且 **§4.1 无可用用户图** 的槽位：

1. **先定槽位角色**（§4.0 表），再写 prompt；风格、构图、色调与 PPT 主题一致，且**与原槽位视觉角色一致**。
2. 调用 Java 生图工具（工具列表中有则必用），参数不足先追问。
3. 将返回的相对路径图片**复制**到 `tmp/`，命名如 `slide-04-bg.png`。
4. 在 `ppt-fill-spec.json` 对应 slide 的 `images: [{ "index": N, "path": "..." }]` 填路径（`index` = `picIndex`）。

#### 按槽位写 prompt（示例）

**主图/背景照片槽**（全彩，无 XML 颜色限制）：
```
治水项目封面主图，城市河道与生态治理实景，16:9 横构图，商务蓝调，无文字无 logo
```

**文字艺术槽**（原 summary 含书法/标语；替换须带字）：
```
商务汇报封面左侧文字艺术，深蓝底+白色书法风格标题「XX河流域综合治理工程」，
留白构图，无人物无风景，风格与原模板水墨笔触一致
```

**效果/单色层**（slide XML 含 biLevel/grayscl，或 summary 为黑白水墨）：
```
不要生成全彩照片；若必须替换，生成高对比单色抽象笔触/纹理，与模板商务蓝一致，可含简短标语
```

生图结果由系统自动展示卡片；**禁止**在回复里贴 markdown 图片链接。

### 4.3 无图页面

纯文字页可不换图；保留模板原排版即可。

## 第五步：组装 JSON 规格

### 5.1 有模板：`ppt-fill-spec.json`（主路径）

```json
{
  "templatePath": "<模板>.pptx",
  "templateId": 1,
  "slideIndex": [],
  "slides": [
    {
      "role": "cover",
      "title": "XX项目方案汇报",
      "subtitle": "某某设计院",
      "date": "2026年7月"
    },
    {
      "role": "content",
      "sourceSlideIndex": 4,
      "title": "用地现状",
      "bullets": ["要点一", "要点二", "要点三"],
      "images": [{ "index": 0, "path": "tmp/slide-04.png" }]
    },
    {
      "role": "closing",
      "title": "谢谢",
      "subtitle": "敬请批评指正"
    }
  ]
}
```

- `templatePath`：用户提供的那个 `.pptx` 在工作区里的路径
- `slides[]`：**数组顺序 = 最终 PPT 页序**（P1、P2…）；每项 `sourceSlideIndex` = 从模板取哪一页的版式
- 每页：`role` + `sourceSlideIndex`（1-based）；复杂页用 **`textPatches`** 精确指定 shapeIndex
- 文字：`title` / `subtitle` / `bullets`（简单页）或 `textPatches`（推荐复杂页）
- 映射：有 `textPatches` 时按明确 patch 执行；没有 `textPatches` 时才根据 `title` / `bullets` 自动推断。复杂模板建议使用 `shapeIndex`，避免脚本猜测文字框。
- 图片：`images[{ index, path }]`；**仅写需要替换的 slot**，保留的示例图省略；`index` 与 `inspect-template` 的 `picIndex` 一致；换图前须完成 §4.0 槽位角色 + XML 效果审读

#### textPatches（精确映射，优先于 title/bullets 推断）

```json
{
  "role": "section",
  "sourceSlideIndex": 3,
  "textPatches": [
    { "shapeIndex": 8, "text": "项目背景" },
    { "match": "YOUR TITLE HERE", "text": "湖泊现状与污染成因深度剖析" }
  ]
}
```

- `shapeIndex`：与 `inspect-template.mjs` 输出一致
- `match`：按 `sampleText` 子串匹配（无 shapeIndex 时）；**同一页多条相同 `match` 按 inspect 顺序依次命中不同 shape**
- `bullets`：该 shape 写入多条 bullet
- `textPatches` 中每项必须提供 `shapeIndex` 或 `match`；脚本发现无法定位文字框时会直接失败，并要求重新检查模板。

完整示例见 `<技能基准目录>/examples/ppt-fill-spec.example.json`。

核对占位：`node .pi/skills/pptx/scripts/inspect-template.mjs tmp/ppt-template-N.pptx`

### 5.2 内容原则

- 单页 bullet 不超过 5 条，每条不超过 25 字；过长拆页。
- 配图用 AI 生图、用户素材，或**保留场景相符的模板示例图**；纯装饰/背景由原 pptx 保留。

## 第六步：生成

**唯一路径（已存模板或用户模板）：**（`tmp/` 应已创建，并已写入 spec / 配图 / 模板副本）

```bash
# 用户已存：若尚未 unpack，先执行下一行；用户模板在 §2.4 已 unpack 可跳过
node <技能基准目录>/scripts/unpack-pptx.mjs <模板>.pptx tmp/ppt-work
node <技能基准目录>/scripts/apply-unpacked-patches.mjs tmp/ppt-work tmp/ppt-fill-spec.json
node <技能基准目录>/scripts/compose-slides-from-spec.mjs tmp/ppt-work tmp/ppt-fill-spec.json
node <技能基准目录>/scripts/pack-pptx.mjs tmp/ppt-work out/汇报.pptx
```

- **禁止** patch 后直接 pack 而跳过 compose（除非输出页数 = 模板页数且 sourceSlideIndex 为 1,2,3…N 顺序）
- **禁止** `Get-Content ... | node` 传 JSON（编码会导致中文变问号）
- spec 须 UTF-8 文件路径
- `pack-pptx` 打包前跑 `validate-unpacked`；打包后再跑 `validate-pptx`；失败 exit 1

**pack 失败时（必做）：**

1. 阅读 `[pptx-unpacked-validate] FAILED` 的 ERROR 行
2. 修正 `ppt-fill-spec.json` / 配图路径 / slide XML
3. 重跑 `apply-unpacked-patches` → `compose-slides-from-spec`（若需）→ `pack-pptx`
4. 向用户说明卡点，继续修正 spec/XML 后重试 pack 流程

## 第七步：交付

本部署没有归档接口。成品写在 `out/` 下就是交付完成。

生成后在回复中：
1. 说明页数与章节结构；
2. 说明哪些页换了图、哪些保留了模板原图；
3. 告诉用户去**输入框左侧的文件夹按钮**（「工作区文件」）里取，并写清路径，例如
   `out/汇报.pptx`。

> **不要说它会作为卡片出现在回复里**——对本技能的产出不成立。那些卡片来自 DSH 的产出
> 累加器，它按渲染意图认定产出：diff 卡片、或 kind 为 `edit` 的通用卡片才算，终端卡片
> 不算。`.pptx` 是脚本打包出来的，所以永远拿不到卡片。承诺一个不会出现的卡片，用户会
> 以为功能坏了。
>
> 同理，**不要把脚本复制到会话工作区再运行**：`jszip` 装在技能目录自己的
> `node_modules` 下，Node 从脚本所在位置向上找依赖，复制走就解析不到，报的
> `Cannot find module` 看起来像环境缺依赖，实际不是。原地运行即可。

## 典型对话场景

### 场景 A：用户先传模板，稍后再做 PPT

1. 用户上传 `公司模板.pptx` 并说「存成模板，叫公司标准汇报」。
3. 回复：「模板已保存（含风格描述），下次您说做 PPT 时可直接选用。」
4. **不强行生成 PPT**。

### 场景 B：用户要做 PPT，工作区里已有模板

1. 用户："帮我做个项目汇报 PPT"。
2. Agent 做需求确认 + `ls *.pptx` 找到模板 → 念出文件名请用户确认。
3. `unpack-pptx.mjs` 解压 → `inspect-template.mjs` 解析版式 → 审模板自带示例图。
4. 大纲确认（含输出页 ↔ `sourceSlideIndex` 对照）→ 写 spec → patch → compose → pack。

### 场景 C：用户要做 PPT，工作区里没有模板

1. 用户："帮我做个汇报 PPT"。
2. Agent `ls *.pptx` 一个都没找到 → **停下来**："这里需要一份 .pptx 模板才能做，本部署
   没有用户模板可选。你有惯用的模板吗？传一份进来我按它的版式填。"
3. **不要**自己拼一份简陋的 bullet 页交差。

### 场景 D：用户传了新模板

1. 用户传入 `.pptx` 并说"以后都用这个"。
2. 模板留在工作区即可，下次 `ls` 就能找到——没有注册这一步。

## 修改已有 PPT

**同会话、`tmp/ppt-work` 仍在**（最常见）：直接改 `tmp/ppt-fill-spec.json` / 配图 → 重跑 patch → compose → pack，覆盖 `out/` 下同名文件。

**跨会话或 tmp/ppt-work 已不存在**：

1. `fetch_artifact(document_id)` 取回原件到 `out/`。
2. 解压到 `tmp/ppt-work` → 改 spec / 配图 → 重跑 patch → compose → pack。
3. 覆盖 `out/` 下的同名文件即可——工作区就是交付面。
4. **不要**从零重写（除非用户明确要求重做）。

## 约束

- **必须**产出真实 .pptx，不要只回大纲或 Markdown。
- 生成物落 `out/`，工作目录为 `tmp/ppt-work`。工作区已经是每用户隔离的，不需要再按租户/会话分层
- 模板不需要「持久化」——它就是工作区里的一个文件，留着下次还在。
- 只在会话工作区内读写。写到工作区之外会被沙箱拒绝，而那个拒绝是你唯一能拿到的信号。
- 必须先需求确认 + 大纲确认，再生成；信息不全时追问，不要编造客户未确认的数据。
- pack 失败时修正 spec/XML 后重试，不要换其他生成方式。
- 没有模板库，因此没有「保存模板」这一步。
