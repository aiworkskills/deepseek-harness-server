# 生成 Word 文档（docx）

把已确认的方案/报告内容生成为**排版规范、可打印/可交付**的真实 .docx，落在会话工作区里。

**禁止**跳过需求确认直接生成简陋正文；**必须**走完下方流程后再调用脚本。

---

## 总流程

```
需求确认 → 大纲确认 → 组装 JSON spec → 生成 → 落到工作区
```

**核心原则**：
- **主路径：程序化新建**（`generate-docx.mjs` + JSON spec → OOXML 二进制）。
- **改稿路径**：spec 留在工作区里，改 spec 重新生成即可——不需要取回二进制，因为 spec 才是文档的源。
- 内容必须来自**已确认**的对话要点、用户上传材料，或业务工具查到的真实数据，**不要编造**客户未确认的数据。
- 生成物只落 `out/`，临时 spec 放 `tmp/`——**都相对会话工作区**，那也是你的当前目录。写到工作区之外会被沙箱拒绝。

---

## 底层原理（Agent 须理解）

Word 的 `.docx` 是 **Office Open XML（OOXML）** 标准：一个 **ZIP 压缩包**，内含一组 XML + 媒体文件。

```
方案.docx（ZIP）
├── [Content_Types].xml      # 包内各部件 MIME 类型
├── _rels/.rels              # 包级关系（指向主文档）
└── word/
    ├── document.xml         # 正文：段落 w:p、文字 w:r/w:t、表格 w:tbl…
    ├── styles.xml           # 样式定义（Heading、Normal…）
    ├── settings.xml         # 文档设置
    ├── fontTable.xml        # 字体表
    ├── numbering.xml        # 编号/项目符号
    ├── media/               # 嵌入图片（若有）
    └── _rels/document.xml.rels
```

**本 skill 的实现路径**（与 pptx 的「解压改 XML 再打包」不同）：

| 层级 | 技术 | 作用 |
|------|------|------|
| Agent | 对话 + JSON spec | 结构化内容、排版意图 |
| 脚本 | Node.js + **`docx` npm 库**（v9） | 用 JS 对象描述 Document / Paragraph / TextRun |
| 库内部 | 生成符合 ECMA-376 的 XML + 打包 ZIP | `Packer.toBuffer()` 输出 `.docx` |

等价关系：

```
JSON spec  →  docx 库的 Document/Paragraph/TextRun  →  word/document.xml  →  ZIP  →  .docx
```

**单位约定**（与 Word 界面换算）：
- 字号：`size` 为 **半磅**（half-points），12pt = `24`，小四 ≈ `24`，三号 = `32`，二号 = `44`
- 边距/缩进/段距：单位 **DXA**（1/20 pt），1 cm ≈ `567`，1 英寸 = `1440`，首行缩进 2 字符 ≈ `480`
- 颜色：6 位 hex，如 `666666`

**当前脚本能力**（`generate-docx.mjs`）：
- 封面：居中标题 + 副标题
- **页眉 / 页脚 / 页码**（`header` / `footer` 字段，见 §3.1）
- 多级节标题（`level` 1/2/3）
- 正文段落（首行缩进、两端对齐）
- 项目符号列表（`type: "bullet"`）
- 富文本段（`runs[]` 混排加粗/颜色）
- 图片占位（`type: "image"`，暂为文字占位，后续可扩展真实插图）
- **表格**（`type: "table"`，支持 `threeLine` / `grid` / `plain` 三种样式）
- **图注 / 表注**（`caption` 字段或 `type: "caption"`）
- **引用块 / 提示框**（`type: "quote"` / `type: "callout"`）
- A4 页边距、默认宋体正文
- **生成前校验**：嵌套结构 / 骨架文档（全文 <500 字）会 exit 1

**与 pptx skill 的对比**：

| | docx（本 skill） | pptx |
|--|------------------|------|
| 主策略 | 代码**从零组装** OOXML | **模板**解压 → patch XML → 重打包 |
| 版式来源 | JSON + 脚本内置排版规则 | 用户/内置 `.pptx` 模板 |
| 精细控版 | 依赖 spec 字段与库 API | 依赖 `inspect-template` + `textPatches` |

## 第一步：需求确认（必做）

用户提出出 Word 后，**先逐项确认**，信息不足时追问，不要假设。可用对话或 `AskQuestion` 分批收集。

### 1.1 文档类型与用途

| 维度 | 要问什么 | 默认推断 |
|------|----------|----------|
| 文档类型 | 方案设计 / 可行性报告 / 技术说明 / 会议纪要 / 合同附件 / 其他？ | 方案设计 |
| 读者与场景 | 给谁看？（业主汇报 / 内部评审 / 归档备案 / 投标） | 从对话推断 |
| 详略程度 | 纲要级 / 完整正文 / 含数据表格与附录？ | 完整正文 |
| 内容来源 | 本次对话、业务工具查询结果、用户上传文档，还是混合？ | 本次对话已确认要点 |
| 硬性结构 | 是否要封面、目录、摘要、附录、签字页？ | 封面 + 正文章节 |

### 1.2 结构与篇幅

| 维度 | 要问什么 | 默认 |
|------|----------|------|
| 章节结构 | 需要几级标题？有无固定模板章节（如「项目概述 / 设计依据 / 方案比选」）？ | 一级章 + 二级节 |
| 篇幅 | 期望页数或总字数？ | 8–20 页量级 |
| 列表与表格 | 是否需要 bullet 清单、**指标对照表 / 三线表**、方案比选表？ | 技术经济指标用 `threeLine` 表格 |
| 目录 | 是否需要 Word 自动目录（TOC）？ | 长文档（>15 页）建议要 |

### 1.3 版式与品牌

| 维度 | 要问什么 | 默认 |
|------|----------|------|
| 页面 | A4 竖版 / 其他？ | A4 竖版 |
| 字体 | 标题/正文字体？ | 标题黑体、正文宋体 |
| 行距 | 固定行距还是 1.5 倍行距？ | 1.5 倍（`lineSpacing: 360`） |
| 现有模板 | 用户是否提供 `.docx` 模板要套版？ | 无则走脚本默认版式 |

### 1.3.1 页眉页脚（必问，不可省略）

**每次出 Word 都必须单独向用户确认页眉页脚**，不要藏在「版式」里一笔带过。可用 `AskQuestion`：

| 维度 | 要问什么 | 默认 |
|------|----------|------|
| 页眉 | 是否需要？内容是什么？（项目名 / 院名 / 章节名 / 无） | 项目全称，居中 |
| 页脚 | 是否需要？内容是什么？（编制单位 / 保密等级 / 无） | 编制单位，居中 |
| 页码 | 是否需要？格式？（第 X 页 / X / 第 X 页 共 Y 页） | 需要，「第 X 页」 |
| 封面 | 封面页是否**不显示**页眉页脚？ | 是（正文从第 2 页起） |
| 院标 logo | 页眉是否要嵌入 logo 图片？ | 无（当前脚本仅文字页眉） |

确认后写入 spec 的 `header` / `footer` 字段（§3.1）。**禁止**不询问页眉页脚就直接生成。

> **有用户 .docx 模板时**：当前主路径为「新建生成」。若用户**强依赖**院标模板（复杂页眉 logo、分节页码），说明限制并询问是否接受「文字页眉页脚 + 内容正确」；完整套模板属于后续扩展，不要假装已支持。

### 1.4 配图与附件

| 维度 | 要问什么 | 默认 |
|------|----------|------|
| 插图 | 哪些章节要图？效果图 / 示意图 / 现场照片？ | 关键章节 1–2 处 |
| 图片来源 | 用户上传或工作区里已有的图，**你自己看过再用**（本部署的模型收图片）；没有合适的就留占位并说明 | 先用用户给的图 |
| 图注 | 是否需要「图1 xxx」居中图注？ | 需要 |

### 1.5 输出

| 维度 | 要问什么 |
|------|----------|
| 文件名 | 如 `XX项目设计方案.docx` |
| 语言 | 中文 / 中英双语 |

**确认方式**：把汇总后的需求清单发给用户过目（类型、章节、**页眉页脚**、版式、配图、文件名），用户点头后再进入大纲阶段。

## 第二步：大纲确认

基于已确认需求与对话内容，给出**章节大纲**（表格或列表）：

```
封面    标题、副标题、编制单位、日期
一、项目概述
  1.1 建设背景
  1.2 建设目标
二、设计依据
三、现状分析（配图：河道现状）
四、方案论证
五、结论与建议
```

用户确认或修改大纲后，进入 **正文撰写**（§2.5），再组装 JSON。**不要**未经确认就生成。

### 2.5 正文撰写（必做，大纲 ≠ 正文）

大纲确认后，Agent **必须撰写完整正文**再写 spec。**禁止**把大纲标题直接当 Word 交付。

| 要求 | 说明 |
|------|------|
| 每节至少 2 段正文 | 或 1 段 + 若干 bullet；每段 ≥ 80 字（概述节可略短） |
| 二级节独立成 section | 见 §3.2 扁平结构 |
| 内容来源 | 本次对话已确认的要点、用户上传的材料、工作区里的文件；无数据处写「待补充」并告知用户，**不要**用空泛套话充数 |
| 禁止骨架交付 | 不得只有章标题 + bullet 关键词；不得全文「以实测为准」类占位 |
| 数据标注 | 推断/占位数据须与用户确认；未确认的具体数值不要编造 |

**自检**：写 spec 前估算总字数 ≥ 1500 字（10 页报告量级）；否则继续补充正文。

## 第三步：组装 JSON 规格

将**完整正文**写入 **`doc-fill-spec.json`**（UTF-8 文件），完整示例见 本技能基准目录下的 `examples/doc-fill-spec.example.json`（DSH 加载技能时会告诉你基准目录的绝对路径）。

### 3.1 顶层字段

| 字段 | 必填 | 说明 |
|------|------|------|
| `title` | 是 | 封面主标题 |
| `subtitle` | 否 | 封面副标题（单位、日期等） |
| `description` | 否 | 文档属性摘要 |
| `lineSpacing` | 否 | 正文行距 DXA，默认 `360`（约 1.5 倍） |
| `header` | 否 | 页眉 `{ text, alignment?, font?, size?, color? }` |
| `footer` | 否 | 页脚 `{ text?, pageNumber?: true, alignment?, font?, size?, color? }` |
| `sections` | 是 | 章节数组（**必须扁平**，见 §3.2） |

**页眉页脚示例**：
```json
{
  "header": { "text": "地块规划设计方案报告", "alignment": "center" },
  "footer": { "text": "某某设计院", "pageNumber": true, "alignment": "center" }
}
```

### 3.2 `sections[]` — 必须扁平（关键）

`sections` 是**平铺数组**：每个 `{ heading, level, paragraphs }` 是独立条目。
`paragraphs` 里**只能**放正文块（字符串 / bullet / table / image / caption / quote / callout / runs），**禁止**再嵌 `{ heading, paragraphs }`。

**❌ 错误**（会导致 Word 只有章标题、正文全部丢失）：
```json
{
  "heading": "一、项目概述",
  "level": 1,
  "paragraphs": [
    {
      "heading": "1.1 项目背景",
      "level": 2,
      "paragraphs": ["正文写在这里…"]
    }
  ]
}
```

**✅ 正确**：
```json
{ "heading": "一、项目概述", "level": 1, "paragraphs": ["本章引导段…"] },
{ "heading": "1.1 项目背景", "level": 2, "paragraphs": ["正文写在这里…", "第二段…"] },
{ "heading": "1.2 建设目标", "level": 2, "paragraphs": [{ "type": "bullet", "text": "目标一…" }] }
```

| 字段 | 说明 |
|------|------|
| `heading` | 节标题文字 |
| `level` | `1` 章 / `2` 节 / `3` 小节，默认 `1` |
| `paragraphs` | 段落数组，见 §3.3 |

### 3.3 `paragraphs[]` 类型

**纯字符串** — 普通正文（首行缩进、两端对齐）：
```json
"本项目位于 XX 市，治理河段全长 12.3 公里。"
```

**对象 — 普通段**：
```json
{
  "text": "建议采用综合治理策略。",
  "bold": false,
  "alignment": "justify",
  "noIndent": false
}
```

**对象 — 富文本混排**（`runs`）：
```json
{
  "runs": [
    { "text": "结论：", "bold": true },
    { "text": "工程具备实施条件。", "color": "000000" }
  ]
}
```

**对象 — 项目符号**：
```json
{ "type": "bullet", "text": "治理范围 12.3 公里", "level": 0 }
```

**对象 — 图片占位**（待扩展真实插图前先用占位 + 可选图注）：
```json
{ "type": "image", "text": "[图1 河道现状示意]", "caption": "图1 河道现状示意" }
```

**对象 — 表格**（推荐用于技术经济指标、规划条件对照）：
```json
{
  "type": "table",
  "caption": "表1 技术经济指标汇总",
  "style": "threeLine",
  "headers": ["指标名称", "规划条件", "方案取值", "备注"],
  "rows": [
    ["总用地面积", "—", "65911㎡", ""],
    ["容积率", "≤2.8", "2.63", ""],
    ["绿地率", "≥30%", "35%", ""]
  ],
  "columnWidths": [28, 22, 22, 28]
}
```

| `style` | 效果 | 适用 |
|---------|------|------|
| `threeLine` | 三线表（顶线 + 表头下线 + 底线，无竖线） | **默认**，报告/指标表 |
| `grid` | 全网格线 + 表头灰底 | 复杂对照、多列数据 |
| `plain` | 仅顶底线 | 简洁列表 |

**简写**：无 `headers` 时，可设 `"headerRow": true`，把 `rows` 第一行当表头：
```json
{
  "type": "table",
  "style": "grid",
  "headerRow": true,
  "rows": [
    ["指标", "数值"],
    ["行洪标准", "20年一遇"]
  ]
}
```

单元格可加粗/对齐：`{ "text": "2.63", "bold": true, "alignment": "center" }`

**对象 — 表注/图注**（单独使用）：
```json
{ "type": "caption", "text": "表2 方案比选结果", "position": "above" }
```

**对象 — 引用块**（规范摘录、重要结论）：
```json
{ "type": "quote", "text": "「生态优先、安全第一」为本项目基本原则。" }
```

**对象 — 提示框**（关键提醒、待办）：
```json
{ "type": "callout", "text": "注：具体数值待规划条件通知书最终确认。", "fill": "FFF8E6" }
```

### 3.4 内容原则

- 一级标题建议用「一、二、三」或「第一章」等与文档类型一致。
- 单段不宜超过 300 字；过长拆段或拆节。
- 数据、地名、规范编号须与用户提供或检索结果一致，**不要编造**。
- 技术经济指标、规划条件对照等**结构化数据优先用 `type: "table"`**，不要用 bullet 凑合。
- 写 spec 后**先跑脚本**；若 `[docx-validate] FAILED`，按 ERROR 修正 spec 再生成，**不要**直接 archive。

### 3.5 写入 spec 文件

```bash
# 将 spec 写入 tmp/（禁止 PowerShell 管道传中文 JSON）
# Agent 用 write 工具创建 tmp/doc-fill-spec.json
```

**禁止**用 PowerShell `Get-Content | node` 或 `echo` 传含中文的 JSON（会变成 `????`）。**必须**把 spec 写成 **UTF-8 文件**，脚本读文件路径。

## 第四步：生成

1. 用 **write 工具** 写好 `tmp/doc-fill-spec.json`（UTF-8）
2. 运行：

```bash
mkdir -p out
node <技能基准目录>/scripts/generate-docx.mjs out/XX项目设计方案.docx tmp/doc-fill-spec.json
```

成功时 stdout 会打印生成的文件路径；`[docx-validate] FAILED` 则按 ERROR 修正 spec 重跑。

> **不要把脚本复制到会话工作区再运行。** `docx` 库装在技能目录自己的 `node_modules` 下，
> Node 从脚本**所在位置**逐级向上找依赖——脚本待在技能目录里才解析得到。复制到
> `tmp/` 之后向上找永远够不到它，报的是 `Cannot find module 'docx'`，看起来像"环境没装
> 依赖"，于是很容易顺手 `npm install docx` 把它盖过去：那要联网、要几十秒，还在用户的
> 工作区里留下一份 `node_modules`。原地运行即可，依赖已经在镜像里。

---

## 第五步：交付

本部署没有归档接口。文件写在会话工作区里，**再调用一次 `attach_deliverable` 声明它**，
就是交付完成：

```
attach_deliverable(path="out/XX项目设计方案.docx")
```

**这一步不能省。** 脚本产出的文件不会自己出现在回复里——DSH 判定"本轮产出了什么"看的是
渲染意图：diff 卡片、或 kind 为 `edit` 的通用卡片才算，终端卡片不算。而 `.docx` 只能靠跑
脚本打包出来。漏了这一步，用户会看到你说"文件已生成"却没有任何可以点的东西，而且不会有
任何报错提示你。

声明之后，文件就和模型直接写出的 `.html` 一样：回复里出现可点的文件，点开在右侧面板打开，
不支持预览的格式直接下载。

- 成品固定落 `out/`，例如 `out/XX项目设计方案.docx`
- spec 留在 `tmp/doc-fill-spec.json`，**不要删**——它是改稿时唯一的源
- 写在工作区之外会被沙箱拒绝，而那个拒绝是你唯一能拿到的信号

生成后在回复中：
1. 简述文档章节结构与篇幅；
2. 说明配图占位/来源（若有）；
3. 告诉用户点文件卡片即可预览。

## 修改已有 Word

**同会话**：改 `tmp/doc-fill-spec.json`，重跑 `generate-docx.mjs`，覆盖 `out/` 下的同名文件。

**跨会话**：工作区按用户持久保留，所以上次的 spec 通常还在。先读 `tmp/doc-fill-spec.json`；
在的话基于已确认的修改点更新它重新生成，**不要从零编造未讨论过的章节**。spec 不在时（用户
清过工作区，或文档是别处来的）就说明这一点并重新走需求确认——凭 .docx 反推 spec 会丢掉
大量排版信息，得到的是一份看起来像、实则不同的文档。

## 典型对话场景

### 场景 A：用户说「帮我把刚才聊的方案出 Word」

1. 需求确认（类型、章节、版式、文件名）— 可从对话推断部分默认值，但**须用户确认大纲**。
2. 输出章节大纲 → 用户确认。
3. 写 spec → 生成 → 归档。

### 场景 B：用户要正式投标版，强调院标

1. 追问：是否有 `.docx` 模板、页眉页脚、签字页要求。
2. 无模板：说明当前为「标准 A4 黑体/宋体」版式，确认是否接受。
3. 有模板：记录需求，按现有能力生成内容；版式完全套模板标记为后续能力，不虚假承诺。

### 场景 C：用户上传了现状照片

1. 你自己看图 → 匹配到大纲「现状分析」节。
2. spec 中该节加 `{ "type": "image", "text": "[图1 …]" }`（或后续真实插图路径）。
3. 归档说明中标注「图1 来自用户上传」。

## 约束

- **必须**产出真实 `.docx`，不要只回 Markdown 或纯文字。
- **禁止交付骨架文档**（只有标题、无实质正文；或全文 <500 字）。
- **禁止**在 `paragraphs` 内嵌套 `{ heading, paragraphs }`；二级节必须拆成独立 section。
- **必须**在需求确认阶段询问页眉、页脚、页码（§1.3.1）。
- 生成文件只落 `out/`；临时 spec 放 `tmp/`。
- **禁止**在 `agent-runtime` 根目录、`src/` 下写脚本或产物。
- 必须先需求确认 + 大纲确认 + **正文撰写**，再生成；信息不全时追问。
- **禁止** PowerShell 管道传递中文 JSON。
- 禁止编造客户未确认的数据、规范号、工程量。
